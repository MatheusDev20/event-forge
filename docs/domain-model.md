# Domain Model — Glossary & Context Map

_Last updated: 2026-08-22_

The vocabulary here is binding: these words mean exactly this in code, in the
database, and in conversation. If a concept needs a new word, add it here first.

## Context map

```
                    ┌──────────────┐
                    │   Identity   │  who is acting
                    └──────┬───────┘
                           │ (user id only, never user objects)
        ┌──────────────────┼──────────────────┐
        │                  │                  │
 ┌──────▼──────┐   ┌───────▼───────┐   ┌──────▼──────┐
 │   Catalog   │──▶│   Inventory   │◀──│  Ordering   │
 │ what exists │   │ what is free  │   │ what is paid│
 └─────────────┘   └───────────────┘   └──────┬──────┘
   published event    holds, allocation       │ order placed
   defines capacity   the hard part           │
                                       ┌──────▼────────┐
                                       │ Notifications │
                                       │ what was told │
                                       └───────────────┘
```

Arrows are dependency direction. **Inventory never imports from Ordering.**
Ordering asks Inventory to convert a hold into an allocation; Inventory does not
know what an order is.

## Bounded contexts

### Catalog — _what exists_

Owns the descriptive, mostly-read side. Deliberately boring: this context is
where we keep complexity **out**.

- **Event** — a happening at a Venue on a date. Has a lifecycle:
  `draft → published → on_sale → closed → cancelled`. Only `on_sale` events
  accept holds.
- **Organizer** — the account that owns an Event.
- **Venue** — a physical place with a **Seat Map**.
- **Seat Map** — the seating layout of a Venue: sections, rows, seats. Belongs
  to the Venue and is reused across Events.
- **Price Tier** — a named price band for an Event (e.g. "Floor", "Balcony"),
  mapped onto sections of the Seat Map.

### Inventory — _what is free_

The heart of the project. Owns availability and the concurrency rules that make
overselling impossible.

- **Allocation** — the units of capacity an Event puts on sale. Either
  **seated** (one row per seat, tied to the Seat Map) or **general admission**
  (a counter). The two are different enough that they get different strategies,
  and comparing them is part of the exercise.
- **Hold** — a time-bounded, exclusive claim on specific Allocation units by one
  attendee. Has an explicit **expiry**; an expired Hold is worthless whether or
  not anything has swept it yet. Expiry must be enforced at read time, never
  trusted to a background job alone.
- **Reservation** — a Hold that has been converted into a permanent claim
  because payment succeeded. Terminal state.
- **Release** — returning held units to availability, whether by expiry,
  cancellation, or payment failure.
- **Oversell** — the bug this context exists to prevent. The invariant:
  `held + reserved ≤ capacity`, always, under any interleaving.

### Ordering — _what is paid_

Owns the money-shaped workflow and the saga across Inventory and Payment.

- **Cart** — the attendee's in-progress selection, backed by a Hold.
- **Order** — an immutable record of an attempted purchase.
  `pending → paid → fulfilled`, or `pending → failed / expired`.
- **Payment Attempt** — one call to the (simulated) gateway. Carries an
  **Idempotency Key**; retrying with the same key must never charge twice.
- **Ticket** — what the attendee ends up owning. Issued only after an Order is
  paid and its Reservation confirmed.

### Identity — _who is acting_

- **Account** — a person's login.
- **Role** — `attendee | organizer | admin`.

Other contexts hold an account id and nothing else. No context reaches into
Identity's tables.

### Notifications — _what was told_

- **Notification** — a message generated by a domain event. Persisted and
  logged; not actually delivered (see non-goals).

## Cross-context language

- **Domain Event** — a past-tense fact one context publishes and others react
  to: `EventPublished`, `SeatsHeld`, `HoldExpired`, `OrderPaid`,
  `TicketsIssued`. In a modular monolith these start as in-process events; the
  point of naming them now is that they become the seam if anything is ever
  extracted.
- **Saga** — the multi-step, compensatable flow Ordering coordinates:
  hold → charge → reserve → issue, with a compensating release at every step.
